Purpose: Give all four developers one shared contract so stories can be developed independently and merged into one

guest preference/document data. React consumes the REST API using hooks and Axios.

7. Database Constraints & Indexes 
• All primary keys are UUIDs. Generate IDs in the backend/database consistently; never mix integer IDs and UUIDs. 
• Foreign keys: lease_agreements.guest_id → guests.id; lease_agreements.unit_id → units.id; units.property_id → 
properties.id; recurring_invoices.lease_id → lease_agreements.id; maintenance_tickets.unit_id → units.id; 
maintenance_tickets.guest_id → guests.id. 
• Unique constraint: (property_id, unit_number). 
• Prevent duplicate invoices for the same lease and billing period: UNIQUE (lease_id, billing_period_start, 
billing_period_end). This is essential for the UiPath monthly workflow. 
• Indexes: lease_agreements(guest_id), lease_agreements(unit_id), lease_agreements(status), 
recurring_invoices(lease_id), recurring_invoices(payment_status), recurring_invoices(due_date), 
maintenance_tickets(guest_id), maintenance_tickets(unit_id), maintenance_tickets(status), 
maintenance_tickets(priority), document_chunks(document_id). 
• Use database transactions for invoice generation and maintenance status changes.

16. Authentication & Resident Data Rules 
• Every resident API must derive the resident/guest identity from authenticated context where authentication is 
implemented; do not trust a guest_id supplied by the browser as the only authorization check. 
• A resident can read only their own lease(s), invoices and maintenance tickets. 
• Staff/admin endpoints may have broader access, but role checks must be centralized. 
• Never send guest PII to an LLM unless the approved design explicitly requires it and compliance rules permit it. 
• Do not log passwords, tokens, API keys or full sensitive guest data.

21. Recurring Invoice Automation Contract 
UiPath runs on the 1st of each month. It should call the batch-generation API for active leases, then identify/flag overdue 
invoices from the previous cycle. The case study specifies this exact monthly workflow. 
filecite
turn1file0
L36-L38
 
1. Start on monthly schedule. 
2. Determine current billing period. 
3. POST /api/v1/invoices/generate-batch 
4. Record generated/duplicate/failed counts. 
5. Check prior-cycle invoices for overdue status. 
6. Flag overdue invoices. 
7. Write an automation log. 
8. Stop. 
The batch endpoint must be safe to retry. This is why the unique billing-period constraint is mandatory.

27. Final Definition of Done 
• All four stories work inside one React application. 
• All story APIs use /api/v1 and the common request/response envelope. 
• All database tables use the frozen names and UUID/UTC conventions. 
• Resident authorization prevents cross-resident access. 
• Recurring invoice generation is idempotent. 
• Maintenance triage has a clear stopping condition. 
• RAG responses return document sources and do not invent unsupported policies. 
• UiPath monthly invoice generation and overdue flagging work. 
• Application runs through the provided Docker setup. 
• Application is deployed to AWS EC2 and Azure App Service as required. 
• CI/CD gates Dev → QA → UAT → Staging → Production are configured. 
• Logging, monitoring and at least one alert are configured. 
• Team can demonstrate the simulated monthly invoice-generation incident and document the fix in Jira Service 
Management.

29. Important Note on the Baseline

starter already has the shared data model/API/architecture and Docker setup. Therefore, when the actual starter repo is 
inspected, preserve its existing names and contracts wherever they match this document. If a starter implementation differs 
from this design, the team should reconcile that difference once, centrally, before four developers begin independent work.
